# Make the vault key ask first

**Bottom line:** the chip is not what protects you. The prompt is. A TPM (the security chip in most PCs), like DPAPI, will serve any program running as you. What changes things is a TPM-held key that only works after the user approves a Windows Hello, PIN or Touch ID prompt, or touches a security key. That turns "malware silently reads the vault key" into "malware has to get you to approve a prompt, or wait until you unlock and then read memory." KeyHandoff can offer that on roughly two-thirds to three-quarters of desktops. The routes are the Windows Hello signature trick that Bitwarden and KeePassXC already ship, a PIN-sealed TPM key on Linux, and the Secure Enclave on Macs. Everyone else gets a FIDO2 security key or a strong Argon2id passphrase. The design is one random vault key with a separate lock per factor: the best hardware factor on this machine, an optional passphrase, and a printed recovery code. A firmware TPM can be wiped by a BIOS update, so the recovery code is required, not optional. Your own Ryzen 9 3900X has a firmware TPM. Your 2019 ASRock BIOS (P2.20) has it switched off. Update the BIOS first, then turn on "AMD fTPM" and add yourself to the `tss` group. You can build and test most of this on Linux today: the lock-slot format, passphrase, recovery code, TPM PIN slot, process hardening and session lock. The Windows Hello slot waits for Monday.

## The prompt, not the chip, is what stops silent theft

"TPM = real security, DPAPI = fake security" is half right, and the half that's wrong decides the design. DPAPI is not fake. It ties the key to your Windows login, so a stolen disk or backup is useless. What it can't do is stop code running as you, because it hands the key to any such program without asking. KeyHandoff's own `docs/threats.md` already says so, and the Linux Secret Service behaves the same way. The catch is that a plain TPM key has the same weakness. Microsoft's own staff note that the TPM stops a key being copied off the machine, but it still serves valid requests from same-user malware: the "confused deputy" problem ([MS Q&A](https://learn.microsoft.com/en-us/answers/questions/5912130/what-is-the-security-boundary-of-windows-hello-key)). **What actually raises the bar is a key that cannot be used without a fresh human action the OS enforces.** The TPM's job is to make that gate impossible to skip and the key impossible to copy away.

Real infostealers show why this matters and why it isn't magic. When Chrome added a check that only Chrome could decrypt its cookies, **at least five stealer families got around it within roughly two months.** None broke the crypto. They injected code into Chrome, read its memory, drove it over the debug port, or impersonated SYSTEM ([Elastic Security Labs](https://www.elastic.co/security-labs/katz-and-mouse-game)). Stealers now target password managers by name, including KeePass, Bitwarden and 1Password ([Check Point Research](https://research.checkpoint.com/2026/infostealer-riding-the-ai-train/)). I found no report of a stealer cryptographically defeating a prompt-gated hardware key. What they do instead is wait for the vault to be unlocked and read memory, capture the master password, or trigger a real prompt at a believable moment.

The best shipping products state these limits openly. Bitwarden's goal is that "a locked vault - a running app - cannot be unlocked when the device (user-space) is compromised." It also concedes that an attacker who can show a genuine-looking Windows Hello prompt and "get the user to confirm it" wins ([Bitwarden windows.rs](https://github.com/bitwarden/clients/blob/main/apps/desktop/desktop_native/biometric/src/windows.rs)). 1Password says that in its TPM mode it "loses control over what can prompt you" because it delegates to Windows Hello ([1Password Community](https://www.1password.community/1password-at-home-31/security-with-use-the-trusted-platform-module-with-windows-hello-19040)). On Windows, any same-user program can open KeyHandoff's Hello credential by name and ask Windows to sign with it. The user sees an identical prompt, and the classic API can't show which app is asking ([MS Q&A](https://learn.microsoft.com/en-us/answers/questions/5912130/what-is-the-security-boundary-of-windows-hello-key)). On Linux the same holds for the TPM device and for security keys.

| Against same-user malware | Today (DPAPI / Secret Service) | Prompt-gated hardware lock |
|---|---|---|
| Copy vault and key files, open them later or elsewhere | Opens them (the malware runs as you) | **Useless:** the key can't leave the chip |
| Unwrap silently while you're away or the app is locked | Yes | **No:** it needs your approval or touch |
| Guess a short PIN | n/a | Blocked by the TPM's lockout counter |
| Show a real prompt at a believable moment and hope you approve | n/a | Still works. This is the main residual risk |
| Read the key from KeyHandoff's memory after you unlock | Yes | **Still yes:** no OS-level fix for normal apps |
| Lock you out (delete the Hello key, trip the TPM lockout) | n/a | Yes. The recovery code covers this |

macOS is the exception. A Secure Enclave key in the data-protection keychain can only be used by code signed with KeyHandoff's team identity, so other programs can't even trigger the prompt ([Apple TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains); [Apple Platform Security](https://support.apple.com/guide/security/keychain-data-protection-secb0694df1a/web)). On Windows and Linux, the honest promise is "no silent unwrap, and stolen files are useless." It is not "malware can't win."

## About 70% of PCs have a usable TPM, but most Linux desktops can't use theirs out of the box

On Windows the TPM picture is good and getting better. Windows 11 requires TPM 2.0 and ran on **about 70% of Steam users in June 2026** ([Guru3D](https://www.guru3d.com/story/windows-11-tops-on-steam-as-amd-continues-closing-cpu-gap/)) and **about 72–73% of desktop Windows in early 2026** per StatCounter ([PCWorld](https://www.pcworld.com/article/3075245/windows-11-market-share-keeps-climbing-despite-all-the-issues.html)). The Windows 10 holdouts are skewed toward machines that failed the upgrade check. In 2022 enterprise data, 14.66% of systems lacked TPM support, and 20.77% failed the TPM test or had it switched off ([Born City / Lansweeper](https://borncity.com/win/2022/10/15/lansweeper-windows-11-readyness-test-auch-im-oktober-2022-fast-50-der-systeme-nicht-kompatibel/)). Virtual machines almost never have one: only 0.23% of enterprise virtual workstations had TPM 2.0 enabled ([The Register](https://www.theregister.com/2021/09/30/windows_11_workstations/)). My estimate for Windows PCs in use in late 2026 is **72–78% with a working TPM 2.0, 5–10% with one present but switched off, and 12–20% with none**. That estimate is inferred, not measured. No 2025–26 dataset splits "off" from "absent" for home PCs.

The "switched off" group is mostly DIY desktops like yours. Before mid-2021, custom-build motherboards commonly shipped with the firmware TPM disabled ([Tom's Hardware](https://www.tomshardware.com/uk/news/windows-11-tpm-enable-bios-uefi)). Board makers then shipped Windows 11-era BIOS updates that turn it on by default ([XDA on ASUS](https://www.xda-developers.com/asus-is-updating-its-motherboard-models-to-enable-tpm-for-windows-11/)). ASRock lists firmware TPM ("fTPM") on every AM4 300-series-and-newer board ([ASRock](https://asrock.com/news/index.asp?iD=4696)). AMD's fTPM has two quirks that matter here. It caused stutter on Windows until AGESA 1.2.0.7 ([Guru3D](https://www.guru3d.com/story/amd-agesa-v2-1-2-7-microcode-to-fix-ftpm-stutters/)). And **a BIOS update or CPU swap can wipe it**, with a boot prompt along the lines of "fTPM NV corrupted… Press Y to reset" ([Framework Community](https://community.frame.work/t/press-y-to-reset-ftpm/74637); [heise](https://heise.de/-10482872)). So anything KeyHandoff seals to a firmware TPM can vanish on an ordinary firmware update. That is why a recovery path is mandatory.

Linux adds a permission wall on top of the hardware question. Debian, Ubuntu and Pop!_OS give the TPM device `/dev/tpmrm0` to group `tss` (mode 0660), and desktop users aren't in that group. Upstream deliberately keeps the raw device locked down to prevent denial of service ([oss-security](https://www.openwall.com/lists/oss-security/2020/08/06/2); [tpm2-tss udev rules](https://github.com/tpm2-software/tpm2-tss/blob/ede63dd1ac1f0a46029d457304edcac2162bfab8/dist/tpm-udev.rules)). My estimate is that **50–65% of Linux desktops have a TPM enabled in firmware, but only 5–20% let a normal app open it with no setup.** The fix is one root step: a group change or a packaged udev rule. Group membership is not a weakness, because every process of the user gets it. The PIN, not device access, is the gate.

Detection should report four states, not just "yes/no". On Windows, call `Tbsi_GetDeviceInfo`, which returns `TBS_E_TPM_NOT_FOUND` when there is none ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/tbs/nf-tbs-tbsi_getdeviceinfo)). Then try creating a real key. On Linux, check `/sys/class/tpm/`, then actually `open()` `/dev/tpmrm0` and treat EACCES as "needs permission". The four states are absent-or-off, too old (1.2), present but not usable, and usable. When there is no TPM node but `/proc/cpuinfo` shows a Ryzen or a 6th-gen-or-later Intel CPU, say "probably switched off in your BIOS" and link Microsoft's vendor-neutral guide ([Microsoft Support](https://support.microsoft.com/en-us/windows/enable-tpm-2-0-on-your-pc-1fd5a332-360d-4f46-a1e7-ae6b0c90645c)).

### Your X570 has the chip; the 2019 BIOS hides it

## Each operating system has exactly one real cryptographic gate

Each OS has a yes/no "are you the user?" dialog that looks like security and isn't. The real gate on each one is the mechanism that makes a key mathematically unavailable until the user acts.

### Windows: sign with Hello; don't just ask Hello

`UserConsentVerifier` shows a nice Hello prompt but returns only "Verified" or "Canceled". Bitwarden's own comment calls it "a yes/no authorization without any cryptographic backing" ([Bitwarden windows.rs](https://github.com/bitwarden/clients/blob/main/apps/desktop/desktop_native/biometric/src/windows.rs)). Malware just skips it and calls DPAPI. **Adding that prompt to today's DPAPI design would change nothing.** The real gate is the "sign path" shipped by KeePassXC and by Bitwarden's Rust code, and it works from unpackaged Win32 apps like a Tauri build. KeyHandoff creates a named Hello key (`KeyCredentialManager.RequestCreateAsync`, which makes an RSA-2048 key ([Microsoft Learn](https://learn.microsoft.com/en-us/uwp/api/windows.security.credentials.keycredentialmanager.requestcreateasync?view=winrt-26100))) and asks Hello to sign a stored random challenge. That shows the prompt. The signature is then hashed into the key that locks the vault key ([KeePassXC WindowsHello.cpp](https://github.com/keepassxreboot/keepassxc/blob/develop/src/quickunlock/WindowsHello.cpp)). Without the user's face, finger or PIN there is no signature, so there is no key.

The trick depends on the signature coming out the same every time. That holds for RSA PKCS#1 v1.5 padding ([RFC 8017](https://www.rfc-editor.org/rfc/rfc8017)), but Microsoft doesn't document which padding Hello uses. KeePassXC states the assumption and warns it "can change in the future" ([KeePassXC PR #7384](https://github.com/keepassxreboot/keepassxc/pull/7384)). So use authenticated encryption for the wrapped key, so that a changed signature fails cleanly instead of corrupting anything. Keep a recovery path in every case. Hello is not always hardware: without a TPM, "software-based techniques protect the key" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/security/hardware-security/tpm/how-windows-uses-the-tpm)). `GetAttestationAsync()` reports `Success` when a TPM backs the key ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/develop/security/windows-hello-auth-service)). It may also report "not supported" on AMD fTPM even when the key is in the TPM ([1Password Community](https://www.1password.community/discussions/1password/tpm-for-windows-hello-after-restart/112367/replies/112376)), which matters for your hardware. Use it as a label in the UI ("hardware" or "software-protected"), not as a reason to refuse.

The practical pain is window focus. Face unlock fails with `0x80098044` if the prompt opens behind other windows. Bitwarden and KeePassXC both poll for the "Credential Dialog Xaml Host" window every 500 ms and force it to the front ([Bitwarden PR #14953](https://github.com/bitwarden/clients/pull/14953)). Windows 11 24H2 adds `RequestSignForWindowAsync`, which takes a window handle, and windows-rs now binds it ([windows-rs](https://github.com/microsoft/windows-rs/blob/master/crates/libs/windows/src/Windows/Security/Credentials/mod.rs)). Use it when it's present and fall back to the focus hack otherwise. Two other Windows routes are lower priority. A TPM key with its own PIN (Microsoft Platform Crypto Provider) gets the TPM's lockout, which allows 32 failures and forgets one every 10 minutes ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/security/hardware-security/tpm/tpm-fundamentals)). But it needs a second PIN, offers no biometrics, and a captured PIN gives malware silent reuse. Microsoft's new "user-bound keys" never put the secret in normal memory, but they require a signed VBS enclave on Windows 11 24H2+ ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/trusted-execution/vbs-enclaves)). Treat that as one to watch for later.

### Linux: a TPM PIN or a security key, nothing else

Linux has no way to turn a fingerprint into a key. fprintd only reports "matched" or "didn't match", and Matthew Garrett explains that there is no secure channel from the reader to the TPM ([mjg59](https://mjg59.dreamwidth.org/68537.html)). polkit is likewise a yes/no answer. Bitwarden's Linux code says polkit "only returns a yes/no authorization decision and no key material", so its persistent mode is opt-in behind a warning that any same-user process can read the key ([Bitwarden linux.rs](https://github.com/bitwarden/clients/blob/main/apps/desktop/desktop_native/biometric/src/linux.rs)). KeePassXC keeps its polkit-gated key in memory only, so it is gone at restart ([KeePassXC Polkit.cpp](https://github.com/keepassxreboot/keepassxc/blob/develop/src/quickunlock/Polkit.cpp)). **The only two real gates are a TPM-sealed key with a PIN and a FIDO2 security key.**

For the TPM, copy systemd-cryptenroll's `--tpm2-with-pin` design. Seal a random secret in the TPM under an authorization value derived from the PIN. Run the PIN through Argon2id first (at least 64 MiB, with a 2-second target), so the TPM is "a second factor rather than a single point of failure". Bind to no PCRs (boot measurements) by default, because firmware and kernel updates change them ([systemd-cryptenroll](https://www.freedesktop.org/software/systemd/man/latest/systemd-cryptenroll.html)). The TPM's lockout counter makes a 6-character PIN safe against guessing. That counter is global: malware can deliberately trip it to lock you out, so treat it as a known denial-of-service risk. The other models are ssh-tpm-agent and age-plugin-tpm. Both keep the sealed key in a user file, use encrypted TPM sessions so the key never crosses the bus in clear, and warn never to pass a PIN in environment variables, which other processes can read from `/proc` ([age-plugin-tpm](https://github.com/Foxboron/age-plugin-tpm); [ssh-tpm-agent](https://github.com/Foxboron/ssh-tpm-agent)). One Linux-specific weakness: KeyHandoff draws the PIN box itself, so on an X11 session any program can log the keystrokes. Wayland blocks that. Detect `XDG_SESSION_TYPE=x11` and say so. Ship native .deb and .rpm packages for this tier. A Flatpak has no TPM permission short of `--device=all` ([Flatpak docs](https://docs.flatpak.org/en/latest/sandbox-permissions.html)).

### macOS: the Secure Enclave is the strongest of the three

Every Mac that macOS 26 supports has a Secure Enclave: T2 Intel models and all Apple silicon. Apple says Tahoe is the last release for Intel ([Macworld](https://macworld.com/article/2644146/macos-26-features-latest-update-release-date-beta.html); [Apple](https://developer.apple.com/documentation/security/protecting-keys-with-the-secure-enclave)). The enclave holds only P-256 keys. KeyHandoff encrypts the vault key to the enclave key's public half with Apple's built-in ECIES. Unwrapping needs the private half, which is gated by `privateKeyUsage | userPresence`: Touch ID, Apple Watch or the login password. The `security-framework` crate (3.7.0) exposes all of it ([docs.rs](https://docs.rs/security-framework/latest/security_framework/key/struct.GenerateKeyOptions.html)). The condition is that the app is a signed `.app` with a keychain-access-group entitlement and an embedded provisioning profile ([Apple TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains)). Plan CI signing before the macOS port, because ad-hoc dev builds won't be able to create these keys. Avoid `BiometryCurrentSet`: it destroys the key when fingerprints change. Like Secretive, accept that enclave keys can't be backed up or moved ([Secretive](https://github.com/maxgoedjen/secretive)).

## Security keys, phones and passphrases cover the machines that are left

A FIDO2 security key is the universal hardware fallback. Its `hmac-secret` extension returns a fixed 32-byte secret for a given salt, but only after a touch and optionally the key's own PIN. The secret never exists without the device ([Yubico](https://developers.yubico.com/WebAuthn/Concepts/PRF_Extension/CTAP2_HMAC_Secret_Deep_Dive.html)). **About 94% of 325 surveyed keys support it** ([Corbado](https://www.corbado.com/blog/security-key-capabilities.md)), and systemd uses it to unlock disks ([systemd-cryptenroll](https://www.freedesktop.org/software/systemd/man/latest/systemd-cryptenroll.html)). On Windows a normal app can't talk to the key directly; direct HID needs admin ([ctap-hid-fido2](https://github.com/gebogebogebo/ctap-hid-fido2)). So go through `webauthn.dll`. It accepts raw 32-byte salts via `WEBAUTHN_AUTHENTICATOR_HMAC_SECRET_VALUES_FLAG` ([webauthn.h](https://github.com/microsoft/webauthn/blob/master/webauthn.h)), which should make one enrolled key give identical results on Windows and Linux. That cross-platform claim needs testing. On Linux, Mozilla's `authenticator` crate (Firefox's own stack) or libfido2 via `fido2-rs` both work. Two cautions. The secret differs with and without PIN verification, so fix that choice at enrollment. And touch alone proves a person touched the key, not which program asked, so only ask for a touch when the user just clicked Unlock.

Phones are the tempting next step. Since February 2026, PRF (the web name for hmac-secret) works across Windows Hello on 24H2/25H2, iCloud Keychain and Google Password Manager, and phone sign-in over QR and Bluetooth ("hybrid") carries it ([Corbado](https://www.corbado.com/blog/passkeys-prf-webauthn)). A Windows 11 app gets hybrid through the same `webauthn.dll` call. There is one open question I could not settle: whether a phone will answer a native app whose relying-party ID isn't a real web domain. Linux has no hybrid stack. Treat phone unlock as an experiment.

Machines with nothing else fall back to a passphrase, run through Argon2id, a deliberately slow and memory-hungry hash. OWASP's floor is 19 MiB with t=2 ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)). RFC 9106's memory-constrained setting, which Bitwarden ships, is 64 MiB, t=3, p=4 ([RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html#section-4); [Bitwarden](https://bitwarden.com/help/kdf-algorithms/)). A desktop can afford 256 MiB. Published GPU cracking rates conflict by about 10×, from roughly 490 to 1,900 guesses per second ([Specops](https://specopssoft.com/blog/does-argon2-mean-password-uncrackable/)). At about 1,000 per second per GPU, a typical human password of about 40 bits ([1Password](https://support.1password.com/secret-key-security/)) falls to 1,000 GPUs in about a week. A generated 5-word diceware phrase (about 65 bits) would take hundreds of millions of GPU-years. **So the passphrase tier must generate the phrase, or reject weak ones.** Tuning the parameters matters far less than the phrase. Argon2id does nothing against a keylogger.

Recovery is where hardware schemes usually fail users. Signal's Linux users lost their message history when the keyring backend changed underneath it ([Gentoo Forums](https://forums.gentoo.org/viewtopic-p-8841636.html)). The established answer is envelope encryption: one random key, wrapped separately by each factor, plus a 128-bit printed code like 1Password's Emergency Kit, which "can't" be recovered by the vendor ([1Password](https://support.1password.com/secret-key-security/)). And never fall back silently to plaintext, the way `gh` does when no keyring is available ([gh manual](https://cli.github.com/manual/gh_auth_login)).

## Recommended design: one vault key, many locks

Keep the existing 32-byte master key exactly as it is: it becomes the vault key. Your architecture doc already says hardware wrapping "only changes how the master key is wrapped". Replace the single DPAPI or Secret Service copy with a small, unencrypted `keyslots.bin`, like LUKS key slots. Each slot records its kind, its non-secret parameters (salt, challenge, credential ID, sealed TPM blob, Argon2 settings) and the vault key encrypted with ChaCha20-Poly1305 under a key derived through HKDF, with a distinct label per slot kind. The slot header is bound in as associated data. **Any one slot opens the vault.** Adding a slot needs one unlock first. `os::master_key` in `src-tauri/src/os/{windows,linux}/protect.rs` is the seam. The `protection` setting that already prevents silent backend switches becomes the slot list.

| Tier | Windows | Linux | macOS | Prompt | Malware gets the key… |
|---|---|---|---|---|---|
| **1. Built-in hardware + prompt** | Hello sign path (labelled "hardware" or "software") | TPM2 sealed + Argon2id PIN | Secure Enclave + userPresence | Face/finger/PIN; PIN; Touch ID/password | only if you approve a prompt, or from memory after unlock |
| **2. External hardware + touch** | FIDO2 via webauthn.dll; phone via hybrid (experimental) | FIDO2 via HID | FIDO2 (rarely needed) | Touch (+ key PIN) | only if you touch the key when it asks |
| **3. Passphrase** | Argon2id, 256 MiB, t≥3, p=4, generated 5–6 words | same | same | Typed phrase | by keylogging, or offline only with a weak phrase |
| **4. "Remember on this computer" (opt-in, warned)** | DPAPI | Secret Service / 0600 file | n/a | None | silently (today's behaviour) |
| **Recovery (always)** | 128-bit printed code | same | same | Typed once | only if someone finds the paper |

The default for a new profile is the best tier the machine offers, plus the recovery code. A passphrase is offered alongside, and is required only where no tier 1 or 2 exists. A "both factors" mode (hardware AND passphrase, combined into one key) can come later; Microsoft staff suggest it as a mitigation for a hijacked prompt ([MS Q&A](https://learn.microsoft.com/en-us/answers/questions/5912130/what-is-the-security-boundary-of-windows-hello-key)). Unlock once per session. Lock on idle timeout, screen lock and sleep. Optionally re-prompt for Send and Safe Copy. Because prompts are the security, only prompt when the user has just acted, and tell users plainly that a prompt they didn't trigger is an attack.

Memory hardening is the remaining gap. Keep the key only in the Rust core process, never in the WebView. On Linux call `prctl(PR_SET_DUMPABLE, 0)`, which blocks same-user debugger attach and `/proc/pid/mem` reads ([kernel Yama docs](https://docs.kernel.org/admin-guide/LSM/Yama.html); [Bitwarden](https://github.com/bitwarden/clients/blob/main/apps/desktop/desktop_native/core/src/process_isolation/linux.rs)). Use `memfd_secret` where the kernel allows it ([man7](https://man7.org/linux/man-pages/man2/memfd_secret.2.html)), plus `mlock` and `zeroize`. On Windows, set a restrictive process DACL with `secmem-proc`, which its author says "can by no means promise any security" ([secmem-proc](https://github.com/niluxv/secmem-proc)). It still stops naive memory readers. KeePass's CVE-2023-32784, which leaked the master password from memory dumps, shows that leftover copies are a real bug class ([Tenable](https://tenable.com/cve/CVE-2023-32784)).

## Conclusion

The key reframe is that **hardware doesn't make KeyHandoff safe from malware. It makes theft visible.** Today a stealer reading `master.key` leaves no trace, and the user never knows. With a prompt-gated lock, the attacker has to either show a prompt the user didn't ask for, which is noticeable and teachable, or catch the key in memory during an unlocked session, which shrinks with short sessions and hardening. That is the same bar the best password managers reach. It is materially better than Chrome-style "is it really me asking?" checks, which fell within weeks. The biggest risk to users isn't malware but lockout. Firmware TPMs wipe themselves on BIOS updates and Hello containers reset, so the printed recovery code is what lets you ship hardware protection at all.

Three things remain uncertain and are worth testing early. First, whether Hello signatures stay deterministic across Windows 10 and 11 builds. Second, whether AMD fTPM reports Hello attestation correctly, which your own machine can show on Monday. Third, whether phones will serve PRF to a native app. If the third works, a phone becomes the universal second factor on Windows, and the passphrase tier shrinks to a recovery role.
